这张图画的是：运营同学在页面上的每一次操作（填表、确认、请求推荐……）进入后台后，会依次经过哪些步骤、在哪儿分岔、在哪儿结束。
依据 app/graphs/campaign/graph.py 里的实际连线整理；图里每个中文方块，都能在同目录 nodes.py 找到对应函数（方块底部小字）。

跟着一个例子走一遍

场景：运营要建一个「春季新品」投放活动，并让系统推荐合适的达人。注意：用户每操作一次，流程就完整跑一遍，不是挂在那里一直等。

  1. 用户填预算，点「下一步」 → 流程走：1 准备 → 2 识别（这是填表）→ 3 写入草稿 → 4 校验 → 发现信息齐了、只差用户确认 → 生成操作预览 → 结束。
  2. 用户点「确认创建」 → 流程再跑一遍：2 识别（这是业务确认）→ 3 写入草稿 → 4 校验 → 提交业务操作，真正调 Java 创建活动 / 任务 → 结束。
  3. 用户点「帮我推荐达人」 → 流程再跑：2 识别（这是推荐启动请求）→ 推荐预览（去 Java 读任务，生成「是否启动推荐」确认）→ 结束。
  4. 用户点「确认启动推荐」 → 流程再跑：2 识别（这是推荐确认）→ 执行推荐操作，真正启动推荐 → 结束。
  5. 系统每隔一会儿查一次进度 → 流程再跑：2 识别（这是进度查询）→ 执行推荐操作，拉取结果、存成快照 → 结束。
  6. 信息不全的时候 → 会走到「等待用户补充」。但这一步还没实现，走到就直接报错，这是目前最明显的缺口。

名词对照表

图中每个方块对应的代码函数，以及它现在到底能不能跑。

图中的方块说白了在做什么现状
1 准备初始状态prepare_context确认有草稿、记下版本号，别的都不做能跑
2 识别事件类型interpret_event看用户这次是什么操作，决定走哪条路能跑（纯文字会报错）
3 写入草稿apply_event把填写 / 选择 / 确认写进草稿能跑
4 校验并决定下一步validate_and_route检查缺什么，算出「下一步动作」能跑
5 等待用户补充wait_for_user本应暂停流程等用户回复未实现，会报错
推荐预览prepare_recommendation_preview读 Java 任务，生成「是否启动推荐」确认要接 Java 后台
执行推荐操作execute_recommendation_operation启动推荐 / 查进度 / 出结果后存快照要接 Java 后台
生成操作预览prepare_operation_preview生成「将要创建什么」的预览，等用户确认能跑
提交业务操作reserve_business_operation真正调 Java 接口创建活动 / 任务要接 Java 后台
底部两条链（6 个方块）run_recommendation / select_candidates / ...推荐跑批、候选挑选、最终确认与提交未实现且走不到
草稿用户正在填、还没提交的一份数据。流程每一步都在改它，它也决定「下一步做什么」。
事件用户在前端的一次操作：填了一格、选了一个活动、点了确认……
下一步动作草稿上的一个标记，值是「等用户 / 要预览 / 要提交 / 结束」之一，判断分支就看它。
快照推荐结果的一份存档；之后的挑选和确认都以它为准，避免结果被改乱。
轮询隔一会儿问一次「推荐算好了没」，直到出结果。
条件分支先判断条件，再从多条箭头里选一条走（图中蓝色虚线）。

现在真正跑得通的路线

开始 → 准备初始状态 → 识别事件类型 →（普通操作）写入草稿 → 校验并决定下一步 → 生成操作预览 / 直接结束。 两个推荐步骤和提交业务操作代码已写好，但必须先接上 Java 后台服务，否则会报「未配置」。

「等待用户补充」是断头路

图左侧那条回环（用户补充后回到第 1 步）在纸面上存在，但「等待用户补充」节点直接抛错—— 因为暂停 / 恢复所需的持久化还没做。所以运行期只要走到这里就中断，回环走不回来。

底部两条孤链和「审核」死分支

推荐跑批、最终提交这两条链没有任何箭头指向它们，永远不会执行； 另外代码里把「审核」分支映射到了「等用户确认选择」，但判断函数永远不会返回「审核」，这条分支也是死路。
